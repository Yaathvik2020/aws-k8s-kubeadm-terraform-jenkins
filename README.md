# Kubernetes via kubeadm on AWS - Terraform + Jenkins, Fully Automated

Terraform creates everything on AWS: a VPC with public/private subnets, a
bastion host, master and worker EC2 instances, security groups, and even the
SSH keypairs used to reach them. Jenkins runs the whole thing end-to-end with
only AWS credentials - no SSH keys to manage by hand anywhere.

## Architecture

```
Jenkins --(AWS creds only)--> Terraform
                                   |
                                   | creates:
                                   |   VPC, public + private subnets, NAT Gateway
                                   |   Bastion EC2  (public subnet, public IP)
                                   |   Master EC2   (private subnet, no public IP)
                                   |   Worker EC2s  (private subnet, no public IP)
                                   |   SSH keypairs (generated by Terraform itself)
                                   v
                              Terraform --SSH--> Bastion
                                                     |
                                                     | uploads node key + scripts
                                                     +--SSH--> Master (private IP)
                                                     +--SSH--> Worker(s) (private IP)
```

Security is enforced at the network layer, not just by convention:
- The bastion's security group accepts SSH **only from your IP**, auto-detected
  by Terraform on every apply (or set explicitly via `allowed_ssh_cidr`).
- The master/worker security group accepts SSH **only from the bastion's
  security group** - not from the internet, not even from other things in the VPC.
- Master/worker have **no public IP at all**; outbound internet (for `apt`,
  pulling images) goes through a NAT Gateway in the public subnet.

```
    ├── keys.tf                  # Terraform generates both SSH keypairs

    ├── bastion.tf                # bastion EC2 instance + SSH-ready wait
    ├── nodes.tf                  # master + worker EC2 instances
    ├── main.tf                   # uploads key/scripts, relays bootstrap via bastion
    ├── variables.tf
    ├── outputs.tf                # includes sensitive key outputs for manual access
    ├── terraform.tfvars.example
    ├── backend.tf.example        # REQUIRED reading - state holds private keys
    └── scripts/

        └── master-init.sh        # kubeadm init + Calico, runs on master only
```

## Prerequisites

1. **An AWS account** and either:
   - An IAM role attached to the machine/instance running Jenkins (recommended), or
   - An IAM user's access key/secret added to Jenkins as "AWS Credentials"
     (Manage Jenkins → Credentials), ID `aws-terraform-creds`

   Minimum IAM permissions needed: EC2 (full), VPC (full), and whichever S3 +
   DynamoDB permissions your state backend needs. Scope this down for
   production use rather than using `AdministratorAccess`.

2. **An S3 bucket + DynamoDB table for Terraform state** (create these once,
   manually, before first run):
   ```bash
   aws s3api create-bucket --bucket your-terraform-state-bucket --region ap-south-1 \
     --create-bucket-configuration LocationConstraint=ap-south-1
   aws s3api put-bucket-encryption --bucket your-terraform-state-bucket \
     --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
   aws dynamodb create-table --table-name your-terraform-lock-table \
     --attribute-definitions AttributeName=LockID,AttributeType=S \
     --key-schema AttributeName=LockID,KeyType=HASH \
     --billing-mode PAY_PER_REQUEST
   ```
   **This step matters more here than in a typical Terraform project**: this
   project's state file contains the plaintext SSH private keys Terraform
   generates (see `keys.tf` and the sensitive outputs). Local unencrypted
   state is not acceptable for this repo - always use the encrypted S3 backend.

3. Copy `terraform/backend.tf.example` to `terraform/backend.tf` and fill in
   your bucket/table names.

4. Copy `terraform/terraform.tfvars.example` to `terraform/terraform.tfvars`.
   `allowed_ssh_cidr` is optional - leave it unset and Terraform auto-detects
   the public IP of whoever runs `terraform apply` (your laptop, or the
   Jenkins agent) and allows only that. Set it explicitly only if you want a
   *different* IP allowed than the one running apply. Nothing in this file is secret.

5. This folder pushed to a **Git repo** Jenkins can check out.

## Step 1 - Test locally first (recommended before touching Jenkins)

```bash
cd terraform
terraform init
terraform plan
terraform apply
```
This provisions the VPC/bastion/master/workers, generates both SSH keypairs,
waits for the bastion to boot, uploads the node key and scripts to it, and
has the bastion relay `kubeadm init`/`join` to master and workers in turn.
A copy of the kubeconfig is also pulled onto the bastion (`~/kubeconfig`)
during the same run, so you don't need to reach the master directly afterward.

Check the result - just one hop, straight to the bastion:
```bash
terraform state list  --> all file in the state.tf

terraform output -raw bastion_private_key_pem > bastion_key.pem && chmod 600 bastion_key.pem
terraform output -raw node_private_key_pem > node_key.pem && chmod 600 bastion_key.pem
scp -i bastion_key.pem ubuntu@$(terraform output -raw bastion_public_ip):~/kubeconfig ./kubeconfig
export KUBECONFIG=./kubeconfig
kubectl get nodes
```

## Step 2 - Jenkins pipeline (fully automated, no manual gate)

1. **New Item → Pipeline → Pipeline script from SCM**, pointed at this repo,
   script path `Jenkinsfile`.
2. **Build Now** is the only human action needed. From there: init →
   validate → plan → apply (creates all AWS resources + bootstraps the
   cluster) → verify (polls until every node is `Ready`).
3. **Zero-click triggers**: enable the git-push webhook, or uncomment
   `triggers { cron('H 2 * * *') }` at the top of the `Jenkinsfile`.

**Teardown** is a separate job pointed at `Jenkinsfile.destroy` - it removes
every AWS resource this project created (VPC, instances, NAT Gateway, keys).
Kept as its own job so destroying real infrastructure and billable resources
is always a deliberate, separate trigger.

## Cost note

This creates **billable AWS resources**: a NAT Gateway (charged hourly plus
per-GB), 1 bastion + 1 master + N worker EC2 instances, and an Elastic IP.
Running `terraform destroy` (or the destroy pipeline) when you're done avoids
ongoing charges - nothing here is "free tier eligible" by default except
possibly the bastion's `t3.micro`.

## Common issues

- **`terraform apply` hangs on wait_for_bastion** → check `terraform output
  allowed_ssh_cidr` to see what CIDR was actually applied. If you're behind
  a VPN, NAT, or your IP changed since the last apply, that value may no
  longer match where you're actually connecting from - just re-run `terraform
  apply` to re-detect it (the security group rule updates automatically).
- **Bastion up, but can't reach master/worker** → check `security_groups.tf`:
  the node SG's SSH rule must reference the bastion SG's ID, and both
  instances must be in the same VPC/subnet routing.
- **`AmazonWebServicesCredentialsBinding` step fails in Jenkins** → install
  the "CloudBees AWS Credentials" plugin, or switch to an IAM instance role
  and remove the `withCredentials` wrapper entirely.
- **Re-running the pipeline** → `kubeadm init` is skipped if the master is
  already initialized, so re-applies are safe.
